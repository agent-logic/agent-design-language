# Issue 297: Preserved Projection Recovery Protocol

## Purpose

Issue-store commits can fail after a new projection has been installed. The store may then restore the last verified projection while retaining the rejected projection as evidence. Issue #297 adds a typed, lock-owned protocol that can classify this interrupted namespace, restore a verified canonical projection without discarding evidence, and separately remove only a specifically authorized archived candidate.

This protocol is recovery authority, not an excuse to make ordinary commits tolerant of ambiguous state. Ordinary commits continue to fail closed while an unresolved recovery namespace exists.

## Namespace and identity model

For issue `N`, the owner operates only beneath `.csdlc/issues` while holding the existing issue lock:

- `N/`: canonical projection.
- `.N.backup`: prior projection retained by a failed commit.
- `.N.rollback-preserved`: rejected projection retained for evidence.
- `.N.recovery/<operation-id>/`: append-only recovery receipts and archived candidates. For cleanup of that completed recovery, cleanup receipts are append-only files in this already-existing attempt directory, named by the distinct cleanup operation id; the cleanup ledger never lives inside the private delete namespace that it authorizes.

Every candidate is opened without following symlinks and classified as absent, regular directory, symlink, or unsupported node. Enumeration is anchored to retained directory handles and never resolves a child through an untrusted absolute path. The manifest has one entry for every directory and regular file: relative byte-safe path, node type, device, platform mount identity, inode, ctime, link count, uid, gid, mode, size, and file digest. Platform mount identity is Linux `statx` mount ID when available; on macOS/BSD it is the `fstatfs` filesystem ID paired with device; unsupported platforms must provide an equivalent stable handle-derived mount identity or reject recovery. Symlinks and special nodes are rejected; every node must remain on both the candidate root's device and mount identity; visited `(mount,device,inode)` tuples must be unique; and every regular file must have link count one. Directory link counts are recorded and revalidated but are not required to be one because ordinary subdirectories increment them. Candidate nodes must have the same uid/gid as the canonical issue-store root and must not be group- or world-writable. A regular-directory candidate is valid only when all expected issue files are contained beneath that directory, its canonical record parses, its issue number matches `N`, its card projections agree with the record, and two anchored enumerations match. Retained root and per-node handles remain live through the namespace operation. Immediately before and after each rename or captured-unlink exchange, the whole manifest and every retained node identity are revalidated. A digest or root-directory identity alone never authorizes rename, replacement, or deletion.

## Typed operations

### Classify

`classify_preserved_projection` is read-only under the issue lock. Its request carries issue, actor, reason, and one tagged CAS anchor:

- `verified_canonical { generation, record_digest }`: the canonical projection must be valid and match.
- `expected_canonical_absent { backup_generation, backup_record_digest }`: canonical must be absent and the named backup must be valid and match.
- `exact_observed_invalid { canonical_node_identity, observed_tree_manifest_digest }`: canonical must exist as the exact invalid inode/tree observed by the caller; its record is not trusted.

All anchors permit read-only classification. Recovery with `verified_canonical` is permitted only when the verified canonical is the restored prior state and a distinct rejected projection plus matching failed-operation lineage exists. Recovery with `expected_canonical_absent` or `exact_observed_invalid` additionally requires exactly one verified backup whose generation/digest match the request and failed-operation lineage. Cleanup accepts only `verified_canonical`. No invalid projection's embedded generation or digest is used as authority.

The result inventories canonical, backup, preserved, and recovery-attempt state, including node type, per-node identities, manifest digest, projection validity, and an explicit disposition:

- `clean`: canonical verified, no recovery candidates.
- `recoverable`: exactly one verified prior candidate and one rejected evidence candidate with unambiguous lineage.
- `already_recovered`: canonical verified and an append-only receipt proves the matching rejected candidate was archived.
- `ambiguous`: more than one eligible prior candidate, conflicting operation lineage, or insufficient evidence.
- `unsafe`: symlink, unsupported node, namespace mismatch, corruption, topology mismatch, or identity drift.

Classify never renames, archives, deletes, or rewrites canonical state.

### Recover

`recover_preserved_projection` requires the exact classify receipt digest, expected canonical generation/digest, expected identities and manifests for every candidate, actor, reason, registered branch/worktree, and a unique operation id. It reopens and revalidates every handle under the issue lock immediately before each namespace transition.

The recovery journal is an immutable, hash-linked attempt ledger stored beneath `.N.recovery/<operation-id>/`. The recovery root and attempt directories are created by handle-relative operations with owner uid/gid and mode `0700`; receipt files are regular, link-count-one, owner uid/gid, mode `0600`, and opened with exclusive create plus no-follow. Existing namespaces with different owner, mode, node type, mount identity, or unexpected entries are unsafe. Each state is written to a new receipt, fsynced, and followed by an fsync of the containing directory. Recovery never appends audit data to an already-installed canonical projection. Instead it builds a complete recovery-owned candidate from the verified prior projection, uses the normal card renderer to append exactly one typed recovery audit event and advance generation, verifies that complete candidate, and installs it atomically.

Every namespace mutation has a durable intent receipt before the mutation and a durable completion receipt after it. An intent records retained source identity/manifest, exact source name, exact deterministic operation-private destination name, required destination state (absent or an exact recorded placeholder), and intended post-state:

1. `PREPARED`: exact classification and topology captured.
2. `ARCHIVE_INTENT`: exact rejected source and required-absent archive destination recorded.
3. `REJECTED_ARCHIVED`: rejected candidate is at the deterministic archive name and the issue/recovery parents are fsynced.
4. `CANONICAL_CREATE_INTENT`: verified prior source, deterministic candidate root and complete per-node construction plan, embedded audit payload, and required-absent root and node destinations recorded before any candidate node is created.
5. For the root and every planned directory or file, a `CANDIDATE_NODE_CREATE_INTENT` records the required-absent handle-relative name, exact type, owner, mode, content source/digest, and intended post-state. Exclusive no-follow creation occurs, the created handle identity is captured, file content and metadata are completed, the node and parent are fsynced, and `CANDIDATE_NODE_CREATED` records the exact inode, mount/device, ctime, owner/mode, link count, size, digest, and completed child set. Candidate construction is leaf-safe and never publishes a partially built tree.
6. `RECOVERY_CANONICAL_PREPARED`: a complete projection derived from the verified prior projection contains the typed recovery audit event (`operation_id`, classify receipt, source identity/digest, rejected archive identity/digest, actor, reason, prior generation/digest, new generation/digest); every planned node has a matching created receipt, every file/directory and parent is durable, and the twice-enumerated final manifest is recorded.
7. `CANONICAL_INSTALL_INTENT`: exact prepared-candidate identity, current canonical state, displaced-canonical destination state, and intended post-state recorded.
8. `RECOVERY_CANONICAL_INSTALLED`: the prepared candidate is canonical and the issue parent directory has been fsynced; any displaced verified prior canonical is retained under the attempt.
9. `CANONICAL_VERIFIED`: the installed canonical projection, embedded audit event, generation, digest, cards, and manifest have been reread and verified.
10. `RECOVERED`: the final receipt records the exact `CANONICAL_VERIFIED` receipt and is fsynced with its parent.

Restart scans the immutable chain. For each intent without completion, it evaluates only deterministic source/destination states: source exact + destination in required pre-state means perform the operation; source absent + destination exact source identity means adopt the already-completed rename and write completion; for an exchange, both names must contain the two recorded identities in either exact pre- or post-order. Both absent, both present after a rename, a replacement identity, or any third state is ambiguous and fails closed while preserving everything. Creation uses a separate exact table: required-absent destination means perform the exclusive creation; a present node is adoptable only when a durable `*_CREATED` receipt records that exact identity and the node revalidates against the recorded type, metadata, content, parent, and construction plan; any present node after a bare `*_CREATE_INTENT`, any partial node lacking its created receipt, or any mismatch is retained and fails closed. A completed child with its exact created receipt is adopted, so a partially constructed candidate resumes only at the first still-absent planned node and never from a fresh walk. Thus a crash after archive rename but before `REJECTED_ARCHIVED`, during candidate construction, or after canonical install but before `RECOVERY_CANONICAL_INSTALLED` is adopted only from durable exact receipts and manifests. It never guesses from a filename. A pre-existing collision, dangling symlink, or candidate introduced after preflight fails unless an exact created/completion receipt already proves the operation-owned inode. `RECOVERY_CANONICAL_INSTALLED` without `CANONICAL_VERIFIED` is resolved by verifying the installed candidate and its embedded operation id, then writing the missing receipts. `CANONICAL_VERIFIED` without `RECOVERED` writes only the final receipt. `RECOVERED` with a missing or mismatched embedded canonical audit is corrupt/ambiguous and fails closed. Because the audit exists in the prepared candidate before installation and `RECOVERED` is last, an audit-durable/receipt-absent state is resumable and a receipt-durable/audit-absent state is never a valid writer-produced state.

The canonical record is not considered recovered until both its embedded typed audit event and the final `RECOVERED` receipt agree on operation id, classify receipt, archived rejected manifest, restored source digest, actor, reason, and prior/current generation/digest. Subsequent ordinary typed commits reject incomplete or ambiguous ledgers but proceed after a complete matching pair.

### Cleanup

`cleanup_preserved_projection` is a separate operation. It requires a completed recovery receipt, the exact archived candidate per-node manifest, a `verified_canonical` CAS anchor, clean registered worktree/branch topology, actor, reason, and a new operation id. Cleanup uses its own immutable ledger. Its receipt files are created exclusively, no-follow, as append-only regular files directly in the already-existing `.N.recovery/<completed-recovery-operation-id>/` attempt directory, with names scoped by the cleanup operation id. That stable directory and the completed recovery receipt are opened and revalidated before the first cleanup receipt; no cleanup receipt is stored in, moved into, or deleted with the private delete namespace.

1. `CLEANUP_PREPARED`: exact canonical, recovery, archive, per-node deletion plan, owner/mode policy, and a required-absent operation-private delete namespace recorded and fsynced.
2. `PRIVATE_DELETE_NAMESPACE_CREATE_INTENT`: the required-absent private directory name, exact directory type, owner uid/gid, mode `0700`, mount, stable attempt-parent identity, and intended empty post-state are recorded in the separate cleanup ledger before creation. The directory is created exclusively by a handle-relative no-follow operation, fsynced with its parent, and `PRIVATE_DELETE_NAMESPACE_CREATED` records its exact identity, metadata, empty manifest, and zero planned children completed. Restart adopts a present directory only when that exact created receipt exists and revalidation proves the same identity, owner, mode, mount, parent, and empty contents; absence after intent permits exclusive creation; any entry, collision, replacement, or metadata drift is retained and fails closed.
3. `ROOT_PLACEHOLDER_CREATE_INTENT`: only after the empty private namespace has its durable created receipt, the required-absent root-placeholder name, exact regular-file type, owner uid/gid, mode `0600`, mount, private-parent identity, empty-content digest, and intended post-state are recorded in the separate ledger before creation. The placeholder is created exclusively by a handle-relative no-follow operation, fsynced with its parent, and `ROOT_PLACEHOLDER_CREATED` records its exact identity and proves the private namespace contains exactly that recorded placeholder and no other child. Restart adopts a present placeholder only from that exact created receipt and exact one-child manifest; absence after intent permits exclusive creation; any additional or mismatched entry fails closed.
4. `ARCHIVE_CAPTURE_INTENT`: archive and created-placeholder identities, names, types, manifests, and exact pre/post exchange ordering recorded. Atomic exchange occurs, then both parents are fsynced.
5. `CLEANUP_CAPTURED`: private capture name contains the exact archive inode/tree; the public archive name contains only the exact empty placeholder; both are revalidated. Any collision/replacement fails closed and is retained.
6. For every planned leaf and then directory, `TOMBSTONE_CREATE_INTENT` first records a required-absent deterministic private name, exact placeholder type/owner/mode, and intended post-state. Exclusive handle-relative no-follow creation, node and parent fsync, and `TOMBSTONE_CREATED` then record the exact placeholder identity. Only afterward does `NODE_CAPTURE_INTENT` record the retained target inode, the exact created placeholder, and the exchange ordering. Atomic exchange captures the node, both parents are fsynced, and `NODE_CAPTURED` records the exact post-order. The captured exact inode is unlinked or `rmdir`ed, its parent is fsynced, and `NODE_REMOVED` is fsynced. Regular files must retain link count one. Directories are removed only when the recorded child plan is complete and the directory is empty.
7. Every public or per-node placeholder disposal has a separately owned, type-matched exchange counterpart. `PLACEHOLDER_DISPOSAL_COUNTERPART_CREATE_INTENT` records a required-absent deterministic name in the private namespace, the exact same supported type as the target placeholder, owner uid/gid, mount, parent identity, and intended post-state. A regular-file counterpart is mode `0600`, link-count-one, and has the empty-content digest; a directory counterpart is mode `0700` and has an exact empty manifest. Any placeholder type other than regular file or directory is unsafe and rejected. Exclusive handle-relative no-follow creation, node and parent fsync, then `PLACEHOLDER_DISPOSAL_COUNTERPART_CREATED` record its exact identity and the updated private-namespace manifest. Only then does `PLACEHOLDER_REMOVE_INTENT` record the target placeholder, created counterpart, exact pre/post exchange ordering, and two deterministic private capture names. Atomic exchange captures the target placeholder under the counterpart name and leaves the exact created counterpart at the target name; both parents are fsynced and `PLACEHOLDER_CAPTURED` records both identities in post-order.

   Disposal of each identity then has its own immutable sub-state. `ORIGINAL_PLACEHOLDER_REMOVE_INTENT` records the captured original identity, its exact private name, type-specific removal operation, parent identity, required pre-state, and exact expected parent manifest after removal. The owner revalidates the captured original and uses `unlink` only for a regular file or `rmdir` only for an empty directory; unsupported types fail closed. After removal the parent is fsynced and `ORIGINAL_PLACEHOLDER_REMOVED` records the absent name and exact post-removal parent manifest. `COUNTERPART_CAPTURE_INTENT` then records the still-exact created counterpart at the target name, its required-absent final private capture name, both parent identities/manifests, and intended post-state. A no-replace rename captures it; both parents are fsynced; and `COUNTERPART_CAPTURED` records the exact identity at the private capture name and the absent target name. `COUNTERPART_REMOVE_INTENT` records that captured identity, its type-specific `unlink` or empty-directory `rmdir`, parent identity, required pre-state, and exact expected parent manifest after removal. After removal the parent is fsynced and `COUNTERPART_REMOVED` records the absent capture name and exact post-removal parent manifest. `PLACEHOLDER_REMOVED` is written only when both identity-specific removed receipts exist, the target and both capture names are absent, and the recorded parent manifests match. The public root placeholder and every private per-node placeholder use this complete sequence; no unrecorded placeholder or unrelated entry is disposed.
8. `CLEANUP_REMOVED`: every planned node and placeholder has a durable removed receipt, archive/public placeholder are absent, the retained private delete namespace is the exact originally created identity and is empty, and public/private parents have been fsynced. The immutable cleanup ledger remains in the separate stable attempt directory; cleanup does not delete or replace that ledger or infer authority from an empty namespace name.
9. `CLEANUP_COMPLETE`: final receipt records the cleanup manifest and `CLEANUP_REMOVED` receipt.

Restart applies the creation table to the private namespace, root placeholder, every tombstone, and every type-matched placeholder-disposal counterpart, and the exchange table to the root exchange, every node exchange, and every placeholder capture. After a creation intent, absence permits exclusive creation; only an exact `*_CREATED` receipt permits adoption; a present node without that completion receipt or with any identity/type/owner/mode drift is retained and fails closed. For placeholder disposal, a durable counterpart-created receipt plus exact pre-order permits the exchange; exact post-order permits adoption and `PLACEHOLDER_CAPTURED`; any type mismatch, collision, or third ordering fails closed. After capture, the exact original placeholder is removed only under `ORIGINAL_PLACEHOLDER_REMOVE_INTENT`. If it is present and exact, restart repeats the type-specific `unlink` or empty-directory `rmdir`; if its name is absent but the parent identity and exact expected post-removal manifest match the intent, restart adopts the completed removal, repeats the parent fsync, and writes `ORIGINAL_PLACEHOLDER_REMOVED`. Any replacement, non-empty directory, unsupported type, or other parent state is retained and fails closed.

The created counterpart may leave the target name only through `COUNTERPART_CAPTURE_INTENT`: source exact plus destination absent performs the no-replace rename, while source absent plus destination exact adopts it and writes `COUNTERPART_CAPTURED` after repeating both parent fsyncs. Every other state preserves all names and fails closed. The captured counterpart is removed only under `COUNTERPART_REMOVE_INTENT`; present-and-exact repeats the type-specific removal, while an absent name with the exact parent identity and expected post-removal manifest adopts the completed removal, repeats the parent fsync, and writes `COUNTERPART_REMOVED`. Thus crashes after either placeholder `unlink`/`rmdir` but before parent fsync, or after parent fsync but before the identity-specific removed receipt, have an exact receipt-, identity-, type-, and parent-manifest-authorized restart path rather than an inference from filename or bytes. Neither identity is reported removed until its own removal intent, parent fsync, exact post-state, and durable removed receipt agree.

A missing captured inode after a durable `NODE_CAPTURED` is treated as removed only when the name is absent and the parent identity/state matches the receipt; restart then fsyncs the parent and writes `NODE_REMOVED`. A present exact captured inode resumes its type-specific removal; a mismatched replacement is retained and fails closed. A crash after unlink or `rmdir` but before parent fsync repeats the parent fsync before the removed receipt; after parent fsync but before receipt, it writes the receipt. A partially removed tree resumes from the per-node plan and receipts, never from a fresh recursive walk. `CLEANUP_REMOVED` without `CLEANUP_COMPLETE` writes only the final receipt. Repeating a complete cleanup returns the same result. It never recursively removes an unclassified path, follows a symlink, disposes an unrecorded placeholder, or treats matching bytes as ownership.

## Crash and restart invariants

- Every recovery and cleanup rename/exchange, file fsync, and parent-directory fsync boundary is an explicit failpoint in tests.
- At every interruption point, a restart either reaches the same recovered state or fails closed with all evidence preserved.
- One verified canonical projection is never replaced by an unverified candidate.
- A rejected projection is never lost as a side effect of recovery.
- A path introduced after classification cannot inherit authority from the classified path.
- Repeating classify, recover, or cleanup with the same operation id is idempotent; a different operation id against an active attempt is rejected.
- Stale or inapplicable tagged CAS, wrong repository topology, wrong branch/worktree, wrong uid/gid, group/world-writable nodes, cross-device or cross-mount trees, repeated per-node identities, regular-file hardlinks, symlink traversal, namespace mismatch, corruption, and multiple plausible backups are terminal classification failures until explicitly resolved by a later typed operation.

## Proof plan

Focused integration tests construct real issue projections and exercise:

- verifier failure, restoration, classify, recover, and a later ordinary typed commit;
- regular-file and directory quarantine collisions, dangling symlinks, and collision insertion after preflight;
- interruption before and after every create intent, exclusive candidate/placeholder/private-namespace/type-matched disposal-counterpart creation, created receipt, rename/exchange, file fsync, parent fsync, completion receipt, per-node unlink or empty-directory `rmdir`, original-placeholder removal intent/removal/fsync/removed receipt, counterpart capture intent/rename/fsync/captured receipt, and counterpart removal intent/removal/fsync/removed receipt, including partial candidate construction and both absent-after-removal restart-adoption windows;
- corrupt, wrong-issue, wrong-generation, wrong-digest, wrong-topology, wrong-owner/mode, cross-mount, hardlinked, and ambiguous candidates;
- unrelated sentinel files in rejected projections surviving recovery;
- repeated classify/recover/cleanup, stale CAS, and exact-digest cleanup rejection;
- existing initialized/ready recovery and #291 behavior unchanged.

The final review is security-, authority-, test-, and evidence-sensitive. Publication is ready-only with `Closes #297`; merge is outside this session boundary.

## Non-goals

- No general-purpose filesystem cleanup command.
- No automatic deletion of preserved evidence.
- No phase rollback, audit rewrite, or manual `.csdlc` editing.
- No merge or closeout.
