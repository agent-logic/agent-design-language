## Summary

Repair the P2 C-SDLC v3 checkout-identity defect that selects proof and install mutation roots from the stable executable’s location instead of authenticated issue-worktree ownership.

## Goal

Ensure every operational proof or install write is authorized against and confined to the invoking bound worktree and exact issue head.

## Required Outcome

At exact review candidate `c24f8fa65ce445b03ce6cd69007307291d78b60c`, findings `A520-ARCH-005` and `C520-CODE-005` show that proof routing walks upward from `current_exe`, while the stable binary resides in the inspection-only primary checkout. The repair must derive the operational repository from authenticated bound context, validate its identity, and use executable location only for provenance.

## Deliverables

- Bound-worktree repository selection for operational proof and install routes.
- Pre-write validation of branch, registration, exact head, shared Git directory, and path containment.
- Explicit operational-versus-historical classification for every callable proof route.
- Integration tests invoking one stable binary from primary and linked worktrees.
- Fail-closed tests for unbound, stale, mismatched, or escaping requests.

## Acceptance Criteria

- Operational repository identity comes from authenticated bound-worktree context, not the executable path.
- Every issue-owned write remains within the registered worktree at the validated exact head.
- Executable location is used only as binary provenance.
- Unbound, wrong-branch, wrong-head, wrong-common-Git-directory, or containment-mismatched requests fail before mutation.
- Dormant historical transition code cannot accidentally expose a callable mutation path.
