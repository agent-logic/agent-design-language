## Proposed first empirical protocol

This proposal needs audit/spec review before adoption or execution.

1. Use a synthetic tool-lending policy domain with explicit return deadlines,
   outage exceptions and registry facts. Author the task corpus for this
   program, retain its license declaration (proposed CC0-1.0), provenance and
   content digest; do not ingest private user conversations as training data.
2. Freeze development tasks D01–D04 and final held-out tasks H01–H04 before
   candidate generation. Assign distinct task families to splits using a
   recorded deterministic seed so near-duplicate variants cannot cross splits.
   Keep final tasks inaccessible to candidate generation and selection; record
   leakage checks and failed candidates. Task identities and seed are proposed
   until spec review freezes the actual corpus digest and split manifest.
3. Permit one typed `task_policy_parameters` / `reasoning_guidance` artifact
   through existing admission per attempt. Guidance data may be included in
   model input. For this first Gate A profile, protect system/instruction
   templates, evaluator/rubric, held-out corpus, authority/credentials, provider
   settings, model weights, source and persistent resident state. Later bounded
   improvement-component changes require a separate reviewed profile. The Runtime owner must implement any eventual accepted promotion
   through the existing governed continuity/birthday path with rollback.
4. Compare incumbent and candidate on identical tasks and resource limits,
   using deterministic constraint checks where possible and a separately
   reviewed scoring rubric for semantic quality. Record all failures, latency,
   tokens and cost; preregister selection and final acceptance thresholds,
   uncertainty treatment and a no-improvement outcome before any run.
5. Treat final evaluation as a one-use decision set. Report selection bias and
   do not tune against final outcomes. A winning offline score cannot establish
   installed success: later proof must show the exact accepted successor,
   native promotion, normal resident-path uptake, persistence/restart recovery
   and rollback under separate explicit execution authority.

No protocol run, budget consumption or quality gain is claimed here. New
provider/cloud work requires separately reviewed scope, exact package/revision,
resource budget and expiry. Existing accepted proof and owners stay intact.
